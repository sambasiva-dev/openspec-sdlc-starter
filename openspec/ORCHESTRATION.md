# Orchestration Rules — sdlc-workflow

**Audience: the main session only.** Read this before delegating an artifact, before running the
post-apply batch, or before archiving a change.

This file is deliberately NOT auto-loaded. It used to live in `AGENT.md`, which loads into every
persona subagent as well as the main session — so all seven personas were being handed a
delegation table, a hard-stop rule about missing subagents, and a batch algorithm that a subagent
structurally cannot act on, all marked "OVERRIDE any default behavior". Roughly 8,100 characters
of instructions that could not apply to the reader.

A subagent that finds itself reading this file has been handed the wrong document.

---

## 🤖 Artifact Authoring Agents (sdlc-workflow)

Each OpenSpec planning artifact is authored by a dedicated **subagent** with its own role prompt,
model, and isolated context. The role DEFINITION is `openspec/roles/<role>.md` (tool-independent);
`.claude/agents/<role>.md` is the Claude Code BINDING that supplies the model and tool grant and
points at it. Edit behaviour in the role file, dispatch in the binding. `openspec/config.yaml` carries
the register and the per-artifact `rules:` that route each one.

| Artifact | Subagent (`subagent_type`) | Model |
| :--- | :--- | :--- |
| `proposal`, `specs`, `business-specification` | `product-engineer` | inherit |
| `design`, `system-architecture` | `principal-architect` | inherit |
| `test-plan` | `sdet-agent` | inherit |
| `tasks` | `tech-lead` | inherit |
| `e2e-test` | `automation-qa` | inherit |
| `performance-test` | `performance-engineer` | inherit |
| `final-code-review` — Review Depth `focused` / `standard` | `senior-staff-reviewer` | Sonnet 5.5 (`claude-sonnet-5-5`) |
| `final-code-review` — Review Depth `escalated` | `senior-staff-reviewer-escalated` | Opus 5.5 (`claude-opus-5-5`), effort `medium` |
| `cost-report` | none — generated by `phase-cost.py` (see Phase cost below) | — |

### Proposal interview relay

The proposal instruction requires an interview before drafting, run in rounds: each round is
one numbered list of every open question. `product-engineer` runs isolated and cannot reach the
user, so the main session relays:

1. Dispatch `product-engineer` for `proposal` as usual. It researches the repo, then returns
   one round of questions (or the playback) instead of a draft.
2. Give the user the whole list **verbatim**, in one message, and wait for the answers. Do not
   add questions of your own, rephrase, answer from your own knowledge, or split the list into
   one-question-at-a-time turns — every extra turn re-sends the whole conversation.
3. Send the user's answers back verbatim, in one message, to the same subagent (`SendMessage` to
   its agent id, so its research context is kept). If that agent is gone, dispatch a fresh one —
   `interview.md` holds the full record, so nothing is lost.
4. Repeat until the user confirms the playback; the subagent then drafts `proposal.md`. Expect
   two rounds plus the playback.

The subagent writes `interview.md`; the main session never edits it. A relayed answer is the
user's words, not the orchestrator's — that is what keeps rule 1 of `AGENT.md` intact.

### Standing rule

When creating or regenerating a sdlc-workflow artifact:

1. Run `openspec instructions <artifact-id> --change "<name>" --json` in the **main session**.
2. Delegate authoring to the mapped subagent with the Agent tool, passing it: `resolvedOutputPath`,
   `template`, `instruction`, `context`, `rules`, and the `dependencies` paths. **`context` is not
   optional** — the schema is project-agnostic, so the stack, test tooling, doc paths, and cost
   profiles reach the subagent only through it.
3. Verify the artifact exists at `resolvedOutputPath` afterwards — plus any write-through file at
   the `context.paths` location the instruction names.

### Hard stop on a missing subagent

If the mapped `subagent_type` is not available, **STOP and tell the user.** Do not author the
artifact in the main session as a fallback, and do not report it as done.

This is the dominant failure mode: agent bindings live in `.claude/agents/` but are registered at
**session start**, so a newly added or renamed agent does not exist until the session is restarted.
A silent self-author looks identical to a successful delegation in the output, which is exactly why
it has to be an error rather than a fallback.

Subagents run in an isolated context and **cannot see the conversation**. Any decision taken
interactively — a gate ruling, a rejected alternative, a correction — must be written into an
artifact, `config.yaml` `context:`, or this file, or it will not reach them.

**Scope:** planning artifacts only. `/opsx:apply` runs in the main session, where implementation
needs to run tests, read failures, and iterate across files.

### Review depth

The six authoring roles run on `inherit` — the main session's model. The reviewer is pinned,
because the reviewer's strength should not depend on whichever model the session was started
with. The proposal's `**Review Depth:**` line picks the binding:

- `focused` (diff scope only) or `standard` (full production-readiness) →
  `senior-staff-reviewer`, Sonnet 5.5.
- `escalated` (full review, Opus-level) → `senior-staff-reviewer-escalated`, Opus 5.5 at medium
  effort.

Both bindings read the same role, `openspec/roles/senior-staff-reviewer.md`; only the model
differs. Model and effort are pinned in each binding's frontmatter, so do not pass a `model` or
`effort` override on the dispatch.

**Raised depth.** If the Sonnet reviewer raises the depth to `escalated` itself (the diff hit a
high-risk trigger the proposal did not anticipate), its review is not the final one. Re-dispatch
`final-code-review` to `senior-staff-reviewer-escalated` before archive, and tell the user why.

## 🧹 Fresh session at phase boundaries

Cost is dominated by cache reads: every response re-sends the whole conversation, so a turn late
in a long session costs many times one early in it. Everything a later phase needs is on disk
(rule 3 of `AGENT.md`), so carrying the conversation across a boundary buys nothing.

At each boundary below, once the phase is done and approved, end the turn with the running cost
line (see Phase cost) and one line telling the user to run `/clear` and then the resume command.
You cannot clear the session yourself, so do not start the next phase in the same turn.

| Boundary | Resume with |
| :--- | :--- |
| `proposal.md` written and approved | `/opsx:continue <name>` (or `/opsx:ff <name>` for the rest of the planning set) |
| `tasks.md` written and approved | `/opsx:apply <name>` |
| `final-code-review` and `cost-report` written | `/opsx:apply <name>` to fix the accepted findings, or `/opsx:archive <name>` |

Before suggesting `/clear`, check that every decision taken in the conversation since the last
boundary — a gate ruling, an accepted or rejected finding, a correction — is written into an
artifact. Anything not on disk is lost by the clear, exactly as it would be for a subagent.

The post-apply batch is not a boundary: it still runs in the same turn as apply finishes.

## 🔧 Fixing review findings — one round

The fixes after `final-code-review` are counted as the `review-fixes` phase. Run them as one round,
not a round per finding:

1. Give the user every CRITICAL, MAJOR and MINOR finding in one message and ask, once, which to
   fix now and which to defer.
2. Dispatch `tech-lead` once to add ALL accepted findings to `tasks.md` as one new task group.
   Record deferred findings as open items in that same dispatch.
3. Implement the group in one apply pass; build and run the affected tests once at the end, not
   after each finding.
4. Re-dispatch `final-code-review` only if a fix touched a risk trigger or the review asked for
   it. Then run `phase-cost.py` once to write `cost-report.md`.

## 💰 Phase cost

`cost-report` records token usage, cost and active time per phase. It is the one artifact no
role authors: `openspec/schemas/sdlc-workflow/tools/phase-cost.py` computes it from the Claude
Code session logs, and you only run the script and check its output.

```bash
python3 openspec/schemas/sdlc-workflow/tools/phase-cost.py --change <name>            # writes cost-report.md
python3 openspec/schemas/sdlc-workflow/tools/phase-cost.py --change <name> --stdout   # running total, writes nothing
```

- **At every approval gate**, run it with `--stdout` and give the user the running total in one
  line (phase just finished, its cost, cost so far) so spend is visible while it can still change
  a decision.
- **After `final-code-review`**, run it without `--stdout` to write `cost-report.md`, and again
  **immediately before archive** so work after the review is counted.
- Never write, estimate or edit a figure yourself. If the script fails, stop and show the user
  its output. Prices live in `tools/pricing.json`; a model missing there is reported as unpriced,
  never guessed.
- Work after the review lands in its own `review-fixes` row; `cost-report` counts only the
  script runs, and nothing after the archive turn is counted.
- Phases are found from markers in the logs: `openspec instructions <artifact> --change <name>`
  and writes to `changes/<name>/<artifact>.md`. Fetch each artifact's instructions with that
  command, as the standing rule says, and the attribution follows.

## ⏩ Post-Apply — author the declared artifact set in one batch

The proposal's `## Artifact Plan` decides which post-apply artifacts a change produces. An
excluded artifact is never written and leaves no file and no waiver — the table row is the
record. `final-code-review` is not selectable; it always runs, at the declared Review Depth.

**Trigger.** When `/opsx:apply` reports every task in `tasks.md` complete and it did not pause,
run the batch immediately, in the same turn. Do not end on "you can archive this change".
`/opsx:continue` runs the same batch and is the resume path if a session ends mid-batch.
`openspec/config.yaml` `operations.apply.guidance` carries this too, because the CLI replaces
the schema's `apply.instruction` with a hardcoded "ready to be archived" string the moment the
last box is ticked.

**Do not run the batch** if apply paused, any task is still `- [ ]`, or the user interrupted. A
half-implemented change produces e2e suites and ledger merges for code that does not exist.

**Build the order.**

1. Read `## Artifact Plan` in `openspec/changes/<name>/proposal.md`.
2. Map each row to an artifact id from `openspec status --change "<name>" --json`. If a row names
   an id that is not in that list, or the table is malformed, STOP and ask. Never fuzzy-match —
   that is how a performance test silently disappears.
3. If the section is absent, treat all four as **Included**. Absence is never exclusion.
4. Author the Included subset in this fixed relative order, skipping excluded rows:
   `e2e-test → performance-test → business-specification → system-architecture`, then
   `final-code-review`, then `cost-report` last (run the script — no subagent).
5. Invoke only the Included artifacts. Do not spawn an excluded one just to let it decline — the
   conditional opener in its instruction is a safety net for a stale session, not the primary
   gate, and spawning it costs a full instruction payload for nothing.

**Excluded artifacts read `ready` forever.** `openspec status` has no way to mark them skipped;
only `skip_specs` produces a `skipped` state and it applies solely to `specs/`. `ready` is not
authorization. Before authoring anything post-apply, from any command, re-read the Artifact Plan.
**For the post-apply artifacts only, this overrides `openspec-continue-change` SKILL.md's
"Create ONE artifact per invocation" and "Never skip artifacts or create out of order"
guardrails.** The five planning artifacts keep them.

**Stop condition.** When every Included artifact and `cost-report.md` exist, report `Artifact
Plan satisfied: N authored, M excluded per proposal` plus the cost report's Total row, and stop. Do not treat leftover `ready` rows as work, and do
not fall into continue's "no artifacts are ready" branch.

Rules that still apply, unchanged:

- Each artifact is authored by its mapped subagent per the table above and `config.yaml` `rules:`
  (`cost-report` excepted: the script generates it).
  Batching changes how many artifacts one invocation produces, never who writes them.
- Each artifact's dependencies are re-read from disk, and each finishes before the next begins.
  Running them concurrently is wrong.
- The four write-through artifacts must write BOTH the change-local file and the `docs/` or
  `tests/` file. Verify both before moving on — nobody is watching between artifacts in a batch.
- **Stop and surface it** if an artifact reveals a genuine problem — a failing verification, a
  contradiction between artifacts, a CRITICAL from `final-code-review`, or a diff that crosses a
  risk trigger for an artifact the plan excluded. Batching removes ceremony, not judgment. An
  exclusion invalidated by the implementation is amended by the user, never overridden by you.
- Before `/opsx:apply` has run, the normal one-artifact-per-invocation behaviour still stands
  (`/opsx:propose` and `/opsx:ff` already batch the planning set).
